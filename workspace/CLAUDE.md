# {{プロジェクト名}} ワークスペース

このファイルは、親フォルダ `xxxxx/` の `CLAUDE.md` から読み込まれる。親フォルダ自体は Git で管理しないため、本体は `xxxxx_document/workspace/CLAUDE.md` に置いてバージョン管理している。

## 構成

```
xxxxx/                     # Git 管理しないフォルダ
├── CLAUDE.md              # このファイルを読み込む 1 行だけ
├── xxxxx_document/        # ドキュメント（要件定義、設計、議事録など）
{{コードリポジトリの構成図}}
```

各リポジトリの役割と clone 元は `xxxxx_document/00_プロジェクト概要/リポジトリ一覧.md` を参照する。

## どこで何をするか

| やること | 起動するディレクトリ |
|---|---|
| 開発環境の確認、設計書の作成・変換、実装タスクへの分解、議事録 | `xxxxx_document` |
| 複数のリポジトリにまたがる変更の検討（API の項目追加など） | この親フォルダ `xxxxx/` |
| タスクの実装と PR の作成（`/project-dev:implement <タスク ID>`） | 対象のコードリポジトリの直下 |
| アーキテクチャの規約と検査の設定（`/project-dev:setup-architecture`） | 対象のコードリポジトリの直下 |

この親フォルダで起動した場合、各コードリポジトリの `.claude/settings.json`（hooks や権限）は適用されない。リポジトリをまたぐ作業では、ここで変更の範囲と I/F を決め、実装はリポジトリごとのセッションで行う。

## 守ること

- Git の操作は、必ず対象のリポジトリの中で行う（`git -C xxxxx_backend ...` など）。1 つのコミットや PR に、複数のリポジトリの変更を混ぜない
- 設計書と実装が食い違ったら、実装を設計に合わせるか、設計の変更を `xxxxx_document` で先に行う。黙って設計と違う実装をしない
- タスクと PR へのレビューのやり取りは Backlog（プロジェクトキー: `{{Backlogのプロジェクトキー}}`）で行う。コードと PR は {{Gitの置き場所}} に置き、PR のリンクを Backlog の課題にコメントする
