# 新しいプロジェクトの作成（軸 A）

ひな型を clone した直後のリポジトリを、新しいプロジェクトのドキュメントリポジトリに作り変える。このスキルはプロジェクトごとに 1 回だけ使い、最後に自分自身（このスキルのフォルダ）と `TEMPLATE.md` を削除する。

## 0. 前提の確認

次の点を確認する。1 つでも満たさなければ、理由を伝えて止まる。

1. カレントディレクトリの名前が `<案件名>_document` で、その親フォルダの名前が `<案件名>` であること。ここから案件名を読み取る。違う場合は、`TEMPLATE.md` の手順 2 のとおりに clone し直してもらう。
2. `TEMPLATE.md` があること（ひな型のままの状態であること）。ない場合は、すでに作成済みのプロジェクトなので何もしない。
3. `.claude/settings.json` のマーケットプレイスの `repo` に、プラグインのリポジトリ（`<オーナー>/claude-plugins`）が設定されていること。空や `YOUR_GITHUB_OWNER/...` のような仮の値なら、ひな型の管理者に `TEMPLATE.md` の「プラグインの参照先を変えるとき」の手順を済ませてもらう。
4. `git status` に未コミットの変更がないこと。

## 1. 対話で聞くこと

次の項目を聞く。推測で埋めない。

**聞き方**：どの項目も自由に記述してもらう答えなので、AskUserQuestion（選択肢から選ばせる道具）は使わない。チャットのメッセージで、項目の一覧を例と一緒に番号付きで 1 回で示し、まとめて答えてもらう。答えが返ってくるまで先に進まない。0 で読み取った案件名も示し、違っていればここで直してもらう。

AskUserQuestion は、この後の手順で「2 つ以上の本当の選択肢から選ぶ」質問（4 の履歴の扱いなど）にだけ使う。選択肢が 1 つしかない質問を作らない。

| 項目 | 例 | 使う場所 |
|---|---|---|
| プロジェクトの表示名 | ACME 会員アプリ | 各文書の見出し |
| GitHub のオーナー（ユーザー名または組織名） | acme-inc | clone 元の URL |
| Backlog のプロジェクトキー | ACME | 課題キーの例、運用ルール |
| リポジトリへの招待の依頼先 | 山田さん | リポジトリ一覧.md |
| コードリポジトリの構成と役割 | backend（API）、frontend（管理画面） | リポジトリ一覧.md、ワークスペースの構成図 |

コードリポジトリは、この時点で GitHub に作られていなくてよい。未作成のものは clone 元を「未作成」とする。

各リポジトリの言語やツールは、ここでは聞かない。コードリポジトリを作るときに、そのリポジトリの `CLAUDE.md` の「開発環境の前提」に書く（`workspace/repo-snippets/README.md` を参照）。

## 2. プレースホルダーの置き換え

まず `--dry-run` で置き換わるファイルを確認してから、本実行する。

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/apply_project.py --slug <案件名> --name "<表示名>" --github-owner <オーナー> --backlog-key <キー> --admin "<依頼先>" --dry-run
```

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/apply_project.py --slug <案件名> --name "<表示名>" --github-owner <オーナー> --backlog-key <キー> --admin "<依頼先>"
```

スクリプトは、`README.md` の冒頭にある「ひな型の案内」（ひな型の段階でだけ表示する囲み）も取り除く。最後に「残っているプレースホルダー」を一覧する。次のものは対話の結果をもとに、手で埋める。

| プレースホルダー | ファイル | 埋める内容 |
|---|---|---|
| `{{コードリポジトリの行}}` | `00_プロジェクト概要/リポジトリ一覧.md` | コードリポジトリの行（リポジトリ、役割、clone 元、既定のブランチ）。clone 元は `git@github.com:<オーナー>/<リポジトリ>.git` の形 |
| `{{コードリポジトリの構成図}}` | `workspace/CLAUDE.md` | 構成図のコードリポジトリの行（`├── acme_backend/  # バックエンド` の形） |

あわせて、`.claude/settings.json` の `permissions.additionalDirectories` に、コードリポジトリ（`../<案件名>_backend` など）を追加する。

最後に `--check` を実行し、プレースホルダーが残っていないことを確かめる。

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/apply_project.py --check
```

## 3. ひな型用のファイルの削除

ユーザーに確認してから、次のものを削除する。

- `TEMPLATE.md`
- このスキルのフォルダ（`.claude/skills/project-new/`）

## 4. Git の履歴とリモート

ユーザーに次のどちらにするかを聞く。

| 選択肢 | 内容 |
|---|---|
| 履歴を作り直す（おすすめ） | ひな型の履歴を消し、「初期構成」の 1 コミットから始める。プロジェクトの履歴にひな型の変更が混ざらない |
| ひな型の履歴を残す | ひな型の変更履歴をそのまま引き継ぐ |

履歴を作り直す場合は、`.git` を削除して作り直すことになるため、実行前にもう一度確認する。

既定のブランチは `develop` にする（作業は `develop` で行い、`main` はリリース済みのドキュメント用）。次の順で進める。

1. `develop` ブランチに切り替える
   - 履歴を作り直す場合: `.git` を削除したあと、`git init -b develop` で作り直す
   - ひな型の履歴を残す場合: `git switch -c develop` で、ひな型の `main` から `develop` を作る
2. `develop` で、変更をすべてコミットする（コミットメッセージ: `初期構成`）
3. `develop` から `main` ブランチを作る（`git branch main`）。作業ブランチは `develop` のままにしておく
4. `origin` を、ユーザーが GitHub に作った空のリポジトリ（`git@github.com:<オーナー>/<案件名>_document.git`）に向ける。ひな型の履歴を残す場合は、ひな型の remote を `template` という名前に変えて残す
5. **push の前に、push 先の URL とブランチをユーザーに見せて確認を取る。** 了承を得たら、**`develop` を先に** push し、続けて `main` を push する（`git push -u origin develop`、`git push origin main`）。空のリポジトリでは、最初に push したブランチが GitHub の既定のブランチになるため
6. GitHub の既定のブランチが `develop` になったことを確かめる（`git ls-remote --symref origin HEAD` の出力が `refs/heads/develop` を指していること）。`develop` でなければ、GitHub のリポジトリの Settings → General → Default branch で `develop` に変えるよう、ユーザーに伝える（設定の変更は代行しない）

GitHub の空のリポジトリがまだ作られていなければ、作ってもらうよう伝えて、push の手前で止まる。リポジトリの作成は代行しない。

## 5. 報告

次の内容を報告する。

1. 置き換えた値（案件名、表示名、オーナー、Backlog のキー）
2. リポジトリ一覧.md に登録したリポジトリの一覧
3. push した先（またはまだ push していない理由）
4. 次の手順: このまま `/project-init` を実行して、自分の環境を整えること。参画メンバーには README の参画手順を案内すること
