# 開発環境のセットアップ（軸 B）

このマシンに、プロジェクトの各リポジトリで作業を始めるための前提を整える。何度実行しても同じ結果になるように動く（すでに整っているものには何もしない）。

## 範囲

| このスキルで行うこと | 行わないこと |
|---|---|
| コードリポジトリの clone | 依存パッケージのインストール（`npm install`、`make install`、`uv sync` など） |
| 各リポジトリが「開発環境の前提」として宣言した、言語の実行環境やツールの確認とインストール | 宣言されていないツールの推測によるインストール |
| 親フォルダの `CLAUDE.md` の配置 | `.env` などの設定ファイルの作成、認証情報の設定 |
| 各リポジトリで最初に実行するコマンドの案内 | コードリポジトリのファイルの書き換え |

依存パッケージのインストールは、各リポジトリの「セットアップ」の節に従って、参画したメンバーが自分で実行する。

## 守ること

- **インストールや clone など、マシンに変更を加える操作は、一覧を見せて了承を得てから実行する。** 確認だけの操作（版の確認、`git ls-remote` など）は確認なしで実行してよい。
- **認証情報（パスワード、API キー、トークン）は扱わない。** 入力を求めたり、ファイルに書いたりしない。必要な場合は、本人が設定する手順を案内するだけにする。
- **コードリポジトリのファイルは書き換えない。** 宣言が足りなければ、追記する内容を報告するだけにする。
- **宣言されていないものはインストールしない。** たとえば `Dockerfile` があっても、Docker が「開発環境の前提」に書かれていなければ確認しない（本番のビルドにだけ使う場合があるため）。

## 0. 前提の確認

1. カレントディレクトリが `<案件名>_document` で、親フォルダが `<案件名>` であること。違う場合は、README の参画手順のとおりに clone し直してもらう。
2. `00_プロジェクト概要/リポジトリ一覧.md` があり、`{{` で始まるプレースホルダーが残っていないこと。残っていれば、プロジェクトの作成（`/project-new`）が終わっていないので止まる。
3. OS を判定する（Windows か Mac か）。インストールの方法を選ぶのに使う。

## 1. リポジトリの clone

`00_プロジェクト概要/リポジトリ一覧.md` の表を読み、親フォルダの直下にあるべきリポジトリを確認する。

まず、clone していないリポジトリの clone 元にアクセスできるかを確かめる。**必ず認証の入力を求めない設定で実行する。** 権限のないリポジトリに対して普通に実行すると、Git の認証画面が出て応答が止まるため。

```bash
GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never GIT_SSH_COMMAND="ssh -o BatchMode=yes" git ls-remote --heads <clone 元>
```

| 状態 | 対応 |
|---|---|
| clone 元が「未作成」 | 何もしない。報告に「未作成」と書く |
| フォルダがなく、アクセスできる | clone 計画に入れる |
| フォルダがなく、アクセスできない | clone しない。アクセス権がない（GitHub ならリポジトリに招待されていない、Azure DevOps ならプロジェクトに参加していない）可能性が高いので、リポジトリ一覧に書かれた依頼先に依頼するよう案内する。SSH の鍵が置き場所に登録されていない可能性もあるので、あわせて案内する |
| フォルダがあり、Git リポジトリで、remote が clone 元と一致する | 何もしない。現在のブランチと未コミットの変更の有無を報告する |
| フォルダはあるが、Git リポジトリでない、または remote が違う | 触らない。報告に書き、ユーザーに判断を委ねる |

clone 計画を見せて了承を得てから、親フォルダの直下に clone し、既定のブランチをチェックアウトする。

## 2. 開発環境の前提を集める

このリポジトリ（`<案件名>_document`）と、clone 済みの各コードリポジトリから、次のものを読んで、必要なツールと版の一覧を作る。

1. **`CLAUDE.md` の「開発環境の前提」の表**（主な情報源）
2. **言語の標準的な版の指定ファイル**（表の版と食い違っていないかの確認に使う）

| ファイル | 分かること |
|---|---|
| `.tool-versions`、`mise.toml` | 複数のツールの版 |
| `.nvmrc`、`.node-version`、`package.json` の `engines` と `packageManager` | Node.js とパッケージマネージャーの版 |
| `.python-version`、`pyproject.toml` の `requires-python` | Python の版 |
| `go.mod` の `go` | Go の版 |
| `rust-toolchain.toml` | Rust の版 |
| `.terraform-version`、Terraform の `required_version` | Terraform の版 |

集めた結果は、リポジトリごとに次のように整理する。

- 「開発環境の前提」の表がない、または例のままのリポジトリは、確認の対象にせず、「宣言がない」と報告する。版の指定ファイルだけがある場合も、推測でインストールせず、表への追記を案内する。
- 表と版の指定ファイルで版が食い違っていれば、報告する（どちらに合わせるかはリポジトリの担当者が決める）。
- **リポジトリ間で同じツールの必要な版が食い違う場合**（例: backend は Node.js 20、frontend は 22）は、1 つの版を入れて済ませず、版を切り替えられる管理ツール（mise、nvm、pyenv など）の利用を提案する。

## 3. 確認とインストール

2 の一覧の各ツールについて、`確認コマンド` を実行し、`必要な版` を満たすかを判定する。結果は次の表にまとめる。

| ツール | 必要とするリポジトリ | 必要な版 | 現在の版 | 判定 |
|---|---|---|---|---|
| Node.js | document、frontend | >=20 | 22.11.0 | OK |
| uv | document | 任意 | （なし） | 未インストール |

- 確認コマンドがアプリの有無のような手作業の行は、OS に合った方法で確認する（Windows なら `winget list --id <ID>`、Mac なら `/Applications` の有無など）。判定できなければ「手で確認」とする。
- 版の比較は、出力から版番号を取り出して行う。取り出せなければ、出力をそのまま見せて「手で確認」とする。

判定が OK でないツールについて、インストール計画を作る。

- インストール方法は、次の順で選ぶ。
  1. リポジトリが版の管理ツール（mise、asdf など）の設定ファイルを持ち、その管理ツールが入っていれば、それを使う
  2. OS のパッケージマネージャー（Windows は winget、Mac は Homebrew）で、公式に配布されているもの
  3. 公式サイトのインストーラー（URL を示して、本人に実行してもらう）
- winget の ID や Homebrew の名前は推測で書かず、`winget search` や `brew info` で確かめてから計画に入れる。
- **依存関係の順に並べる。** 例: Mermaid CLI は npm で入れるので、Node.js の後にする。
- 「必須」でないツールは、入れるかどうかを個別に聞く。
- 版が古いツールは、上書きで更新してよいかを確認する。ほかの用途で古い版を使っている人もいるため、勝手に置き換えない。

計画を見せて了承を得たら、1 つずつ実行し、実行後に確認コマンドで判定し直す。インストール直後は PATH が更新されず、確認コマンドが見つからないことがある。その場合は、ターミナル（または Claude Code）を開き直してから `/project-init` をもう一度実行するよう伝える。

## 4. 親フォルダの CLAUDE.md

親フォルダ `<案件名>/` に `CLAUDE.md` を置く。内容は次の 1 行だけにする。

```
@<案件名>_document/workspace/CLAUDE.md
```

- ファイルがなければ作る（親フォルダは Git 管理しないので、確認なしで作ってよい）。
- すでにあって内容が同じなら、何もしない。
- 内容が違う場合は、差分を見せて、置き換えてよいかを確認する。本人が書き足した内容かもしれないため。

## 5. コードリポジトリの設定の確認

clone 済みのコードリポジトリそれぞれについて、`workspace/repo-snippets/README.md` の内容が入っているかを確認する。

- `CLAUDE.md` に「開発環境の前提」「セットアップ」「テスト・lint・ビルド」の節があり、例のままでなく埋まっているか
- `CLAUDE.md` に、ドキュメントリポジトリ（`../<案件名>_document`）への参照があるか
- `.claude/settings.json` の `permissions.additionalDirectories` に `../<案件名>_document` があるか
- `.claude/settings.json` で、マーケットプレイスと `project-dev@project-plugins` が有効になっているか。マーケットプレイスの `repo` が、このリポジトリの設定と同じ値か

足りないものは、リポジトリ名と追記する内容を報告に載せる。ファイルは書き換えない。

## 6. Claude Code の確認

- `claude plugin list` を実行し、このリポジトリの `.claude/settings.json` の `enabledPlugins` にあるプラグインが有効になっているかを確認する。有効になっていなければ、次のことを案内する。
  1. Claude Code をこのフォルダで開き直し、フォルダを信頼するかの確認で「信頼する」を選ぶ（プロジェクトの設定にあるマーケットプレイスは、信頼したフォルダでしか読み込まれない）
  2. それでも出なければ、`/plugin` の「Marketplaces」で `project-plugins` を更新する
- PR を作るツールにログインしているかを確認する。どちらのツールかは、`00_プロジェクト概要/リポジトリ一覧.md` の「Git の置き場所」で決める。ログインしていなければ、本人がログインのコマンドを実行するよう案内する（代わりに実行しない）。

| Git の置き場所 | 確認のコマンド | ログインのコマンド |
|---|---|---|
| GitHub | `gh auth status` | `gh auth login` |
| Azure DevOps | `az account show`（ログイン）と `az extension show --name azure-devops`（拡張の有無） | `az login`。拡張がなければ `az extension add --name azure-devops`（拡張の追加は、了承を得てからこのスキルで実行してよい） |

## 7. 報告

最後に、次の形で報告する。

1. **結果の一覧**：リポジトリ、ツール、プラグインごとに「OK」「今回対応した」「本人の対応が必要」のどれか
2. **本人の対応が必要なこと**：手順付きで箇条書きにする（例: リポジトリへのアクセス権の依頼、`gh auth login` や `az login`、ターミナルの開き直し）
3. **各リポジトリで最初に実行するコマンド**：各リポジトリの「セットアップ」の節に書かれたコマンドを、リポジトリごとに並べる（このスキルは実行しない）
4. **コードリポジトリに足りない宣言・設定**：2 と 5 で見つかったもの
5. **どこで何をするか**：`workspace/CLAUDE.md` の「どこで何をするか」の表をそのまま示す

本人の対応が必要なことが残っている場合は、対応したあとにもう一度 `/project-init` を実行するよう伝える。
